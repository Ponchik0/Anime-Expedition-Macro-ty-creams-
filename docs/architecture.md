# Архитектурная карта движка

Разбор `Cweamy/Anime-Expeditions-Creams-Macro` v0.14.0 (коммит `f7bdf4d`).
Python 3.14, ~16 000 строк в `core/`, ~11 000 строк в `ui/`.

---

## 1. Общая схема

```
main.py  (3823 строки)
   │  pywebview: создаёт окно, встраивает в него окно Roblox,
   │  поднимает класс Api — это мост JS ↔ Python
   │
   ├── ui/          фронтенд: HTML + CSS + JS в WebView2
   │                вызывает Python как pywebview.api.<метод>()
   │
   └── core/        вся логика: зрение, ввод, окно, прогон матча
```

Важно понимать: **это не десктопное приложение на виджетах, а веб-страница
в окне.** Вся вёрстка — обычные HTML/CSS/JS. Для нашего редизайна это скорее
плюс: переверстать `ui/` можно как обычный сайт, не трогая Python.

### Как окно игры оказывается внутри приложения

`core/dock.py` — «докинг». Два режима:

- **Windows (обычный):** окно Roblox делается дочерним окном нашего окна
  (`SetParent`). Игра физически живёт внутри интерфейса.
- **Cutout-режим:** Roblox остаётся отдельным окном, приклеенным позади дырки
  в нашем окне. Нужен, когда обычный захват экрана возвращает чёрные кадры.
- **macOS:** встроить чужое окно нельзя в принципе — панель и игра просто
  стоят рядом.

Размер окна игры фиксирован: **1152 × 756** (`config.FIXED_WIN_W/H`). Из этого
следует важное: **все координаты в движке — в этой системе**, и задача
«пересчитать под любой размер окна», которая занимала столько сил в AHK-версии,
здесь решена иначе — окно просто всегда одного размера.

## 2. `core/` — по модулям

### Ввод (мышь и клавиатура)

| Модуль | Что делает |
|---|---|
| `mouse.py`, `keyboard.py` | единый кросс-платформенный API: `click`, `move_to`, `tap`, `combo` |
| `_input_win.py`, `_input_mac.py` | платформенные реализации одного и того же набора примитивов |
| `_sendinput.py` | сырой Win32 `SendInput` |
| `keys.py` | таблица виртуальных кодов клавиш |
| `pacing.py` | глобальный «замедлитель»: одна общая задержка во всех точках ввода |

Ввод идёт через `SendInput`, а не `SetCursorPos` — по той же причине, что и
`SendMode Input` в AHK: игры слушают настоящий поток ввода, а простую запись
позиции курсора игнорируют.

`pacing.py` — красивое решение той же проблемы, что в AHK решалась россыпью
`RandSleep()` по коду: одна ручка «Macro Speed» добавляет задержку в общих
точках (`Mouse.click`, `Keyboard.tap`), а не в пятидесяти местах.

### Зрение — **`core/vision.py` (1134 строки), ключевой модуль**

Отвечает на вопрос «где на экране вот эта кнопка».

- Эталоны лежат в `Assets/ui/<имя>/` — **папка на каждое искомое имя**, внутри
  один или несколько PNG-вариантов одной и той же кнопки. Все варианты
  пробуются как взаимозаменяемые.
- Сравнение **в оттенках серого**, не в цвете. Причина ровно та же, что мы
  выстрадали в AHK: текст в этой игре на градиентной заливке, цвет плывёт по
  букве, а яркость кнопки зависит от экрана.
- Матчинг через OpenCV `matchTemplate` с порогом; порог настраивается **на
  каждое изображение отдельно** (Image Manager → sensitivity).
- Несколько источников кадра: `mss` (снимок экрана), `PrintWindow` (свой
  бэкбуфер окна — не мигает), `wgc_capture.py` (Windows.Graphics.Capture —
  для случаев, когда первые два дают чёрный кадр).

Функции, которыми пользуется весь остальной код:
`find_image(hwnd, name, threshold)` и `wait_for_image(hwnd, name, timeout)`.

### Система блоков — как здесь устроена «программа матча»

Это главное архитектурное отличие от моего AHK-макроса.

В AHK было: список юнитов + у каждого точка и число апгрейдов. Жёсткая схема.

Здесь: **Macro Operation** — сценарий из блоков, который пользователь собирает
в UI (экран Creation). Блоки бывают двух фаз:

- **Pre Start** — до нажатия «Start Game» (настройка камеры, лоадаут, ходьба,
  предварительная расстановка);
- **Battle** — во время боя (доставить юнита, апгрейдить, продать, ждать волну).

Типы блоков: `place_unit`, `upgrade`, `sell`, `wait`, `wait_for_wave`, `walk`,
`setting`, `detect`, и т. д.

`core/detect.py` — единственный ветвящийся блок: ищет картинку и выполняет одну
из двух вложенных веток (`then` / `else`). Реализован хитро: вложенность
**разворачивается в плоский список** с двумя служебными операциями перехода,
чтобы движок исполнения остался простым циклом с одним индексом.

### Установка юнита — `_run_place_unit_block` (`runner_blocks.py:1039`)

Как это работает сейчас:

1. Нажать `Z` (сброс текущего выделения), затем **хоткей юнита** — это прямой
   аналог нашей «клавиши слота 1-6».
2. Найти валидную клетку: игра подсвечивает место установки **белым**.
   Ищется белый пиксель в квадрате 38×38 вокруг сохранённой точки; если не
   нашлось — расширяющийся поиск по кольцам радиусом 24 / 48 / 72 px,
   бюджет 8 секунд. Есть галка «игнорировать подсветку» — тогда клик вслепую
   по координате.
3. Клик.
4. Проверка `max_placement_reached` — не упёрлись ли в лимит юнитов.
5. **Верификация:** ищется картинка `unit_exist` (панель информации о юните).
   Если не видно — кликнуть по юниту и проверить снова, до 3 попыток по 2 с.
6. Опция «Keep Placing» — повторить весь цикл целиком до 5 раз.

Оптимизация «quick place»: если подряд идут блоки установки **одного и того же**
юнита, между ними держится Shift — юнит остаётся выбранным, и каждая следующая
установка пропускает нажатие хоткея.

Константы (`runner_constants.py:385-415`):

```
PLACE_SEARCH_BOX_SIZE = 38        поиск белой клетки вокруг точки
PLACE_SPIRAL_RADII = (24, 48, 72) кольца расширяющегося поиска
PLACE_SPIRAL_TIMEOUT = 8.0        бюджет на весь поиск
PLACE_HOTKEY_SETTLE = 0.35        подсветка клетки должна успеть отрисоваться
PLACE_UNIT_CLICK_SETTLE = 0.25
PLACE_UNIT_VERIFY_TIMEOUT = 2.0
PLACE_UNIT_VERIFY_ATTEMPTS = 3
PLACE_RETRY_UNTIL_PLACED_ATTEMPTS = 5
```

#### Выбор точки установки (`#pu-modal`) и снимок по умолчанию

Одно окно на три вызова: кнопка «Set» у блока Place Unit, та же у блока Click и
Настройки → Отладка → Macro Coordinates (`openCoordPicker`). Внутри — вкладки
категорий из `Assets/map/<Категория>/`, сетка карт и холст, на котором клик
превращается в координату.

Готовых карт в поставке нет намеренно: клик по чужому кадру промахивается,
ракурс камеры у каждого свой (`Assets/map/README.txt`). Точный путь один —
«Снимок из игры» (`get_roblox_snapshot`), и раньше его приходилось повторять на
**каждую** точку.

**Снимок по умолчанию для режима.** Кадр сохраняется один раз и дальше
подставляется сам, как только окно открыто для сценария этого режима:

- хранится обычным PNG — `Assets/map/<Режим>/Snapshot.png` (`core/maps.py`:
  `MODE_CATEGORIES`, белый список — имя режима попадает в путь на диске), то
  есть виден и как обычная карта, и удаляется стиранием файла;
- ключ — **режим, а не карта**: точка задаётся в экранных координатах и зависит
  от ракурса камеры, а камеру макрос выставляет одинаково для всего режима;
- сохраняются те самые байты, что человек видел на холсте (`main.py` помнит
  последний снимок в `_map_snapshot_png`), а не новый снимок экрана — к моменту
  нажатия игра нарисует уже другую волну;
- режим сценария выводится из очереди задач (`resolvePlaceUnitMode`): сценарий
  сам по себе к режиму не привязан, зато задачи ссылаются на него по имени.
  Неоднозначно — берётся прошлый выбор, и его можно поменять селектором;
- в режиме выбора координат из Настроек эти органы управления скрыты — там
  режима нет.

### Оформление сейчас

CSS-переменные в `:root`, тем — около десятка (`data-theme-base` /
`data-theme-accent`).

```
--bg-deep: #11131c   --bg-card: #171a26   --bg-surface: #1c2030
--border:  #2a2e42   --text:    #e2e4ef
--brand: #7c9dff   --teal: #45c9b5   --amber: #e3b158
--lilac: #b58ce0   --rose: #d9667a   --sky:  #5aa9e6
```

То есть ровно то, от чего мы уходим: **сине-фиолетовая база**, шесть акцентных
цветов вместо одного, есть тема со стеклом. По подсчёту: **17 градиентов** и
**7 мест с `backdrop-filter` / `blur()`** в `style.css`.

Хорошая новость для редизайна: цвета уже вынесены в переменные, а разметка
размечена классами `rp-panel`. Значит переверстать можно системно, а не
переписывая 2220 строк HTML вручную.

## 4. Что это значит для нас

**Сильные стороны движка, которые нам достались даром:**

- готовый докинг окна игры и фиксированный размер 1152×756 — снимает всю боль
  с пересчётом координат, на которую в AHK ушла половина кода;
- зрелый слой зрения с тремя способами захвата кадра и порогом на каждую
  картинку;
- быстрый встроенный OCR Windows;
- система блоков — гибче, чем моя жёсткая схема «юнит + точка + апгрейды»;
- поиск валидной клетки по белой подсветке — этого в AHK не было вообще,
  и это честнее, чем слепой клик по координате;
- готовые режимы Story / Raid / Challenge / Expedition / Bounty / Crafting;
- Discord-вебхук с отрисованной карточкой результата.

**Слабые места, которые придётся закрывать нам (см. `from_ahk.md`):**

- юнит выбирается **только хоткеем**, поиска по иконке нет — если хотбар
  перемешается, поставится не тот юнит и никто этого не заметит;
- верификация установки **одинарная** (`unit_exist`), нет проверок по деньгам
  и по изменению карты, нет понятия WRONG_UNIT;
- нет аварийного стопа по числу подряд идущих провалов установки (есть только
  по трём поражениям подряд на одной карте);
- нет папки `units/` с автосканом иконок;
- в логах нет фильтра, поиска и экспорта.
